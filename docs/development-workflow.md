# 开发与版本管理

本规范适用于 `code` 仓库。用户已授权使用 Git 管理代码并把重要版本同步到远程 GitHub；重要成果验证完成后正常提交、推送，无需重复请求相同授权。

## 1 目录与工程边界

当前已创建前后端基础工程、脚本与持续集成配置。目录如下：

| 路径 | 用途 |
| --- | --- |
| `frontend/` | Vue 3 前端源码、页面和相关测试 |
| `backend/` | Java 与 Spring Boot 后端、数据库迁移及相关测试 |
| `docs/` | 需求、设计、Scrum 与 AI 记录、测试和演示材料 |
| `scripts/` | 确有需要时加入开发或部署辅助脚本 |

上传课件、转换结果、缓存和日志放在持久化运行目录，排除 Git；数据库备份采用独立受控位置，不默认上传公开仓库。运行目录路径、依赖版本和命令在实现后据实写入 README。

## 2 分支与提交

- `main` 保存已检查的文档基线和可运行增量；文档标签与软件版本区分，当前版本范围见 README 和执行记录。
- 较大功能使用 `feature/course`、`feature/material-reader` 等短期分支，功能完成并验证后合并到 `main`。
- 小范围文档和简单修复可直接在 `main` 提交。跨多天的阶段成果可推送功能分支备份，明确标识未完成状态。
- 一次提交表达一个完整变更，不能把无关文件、临时产物和用户未要求的变更混在一起。
- 保留真实提交历史，不伪造其他成员身份、不回填日期，不擅自重写远程提交。

提交示例：

```text
docs(planning): 建立需求与 Scrum 开发文档基线
feat(course): 实现课程创建与首页展示
feat(material): 实现课件上传与处理状态查询
fix(review): 修复重点定位结果的页码偏移
test(practice): 覆盖重复提交与无答案题统计
```

正文可记录关联的 PB、变更理由和验证结果。修复引用真实缺陷，不能写尚不存在的 Issue 编号。

## 3 推送前检查

1. 检查当前分支、工作区差异和远程更新，保留用户已有改动。
2. 核对提交范围，执行与改动相称的检查；文档检查链接和一致性，代码执行相关构建、测试或操作验证。
3. 确认没有 API Key、密码、用户上传资料或构建产物，必要配置使用示例占位值。
4. 发现远程更新时先正常整合；有冲突则按真实意图解决并重新验证，不使用强制推送覆盖。
5. 提交并推送，确认远程分支和本地目标提交一致。
6. 向用户说明完成内容、验证、提交编号、标签及推送结果；失败如实说明。

Git 能连接和推送不意味着所有新分支、标签或受保护分支一定可写，实际操作结果以 GitHub 返回为准。若保护规则要求 PR，则遵循规则，不绕过。

## 4 里程碑

规划文档基线使用带说明的标签 `docs-baseline-20261027`，与可运行软件版本分开。软件版本从工程初始化后按真实结果创建，不提前创建全部标签。

首轮技术设计使用 `design-baseline-20261027` 保存架构、数据库、接口和验证方案，仍为文档里程碑，不代表工程初始化或技术验证成功。

| 计划版本 | 条件 |
| --- | --- |
| `v0.1.0` | 前后端基础工程及本地启动流程可用 |
| `v0.2.0` | 课程、课件上传与阅读通过验收 |
| `v0.3.0` | 重点清单和页面定位通过验收 |
| `v0.4.0` | 阅读 AI 答疑形成可验证增量，笔记单独推进 |
| `v0.4.1`（候选） | 笔记与答疑内容保存形成可验证增量 |
| `v0.5.0` | 三种习题来源与作答记录通过验收 |
| `v1.0.0` | 完成最终承诺范围、回归和演示准备 |

标签指向已提交的具体成果，记录范围、验证和已知问题，并单独推送对应标签。版本路线可调整，不能把计划表当作已发布清单。更正版本使用后续提交和新版本，不移动已公开的稳定标签。

## 5 配置与 CI

DeepSeek Key 只从后端环境或未提交的本地配置读取，不进入前端、README 示例、测试截图或 Git 历史。初始化时完善 `.gitignore`，排除 `.env`、本地凭据、依赖、构建、运行文件；可提交无真实值的配置示例。

已配置 GitHub Actions，使用 Ubuntu 24.04 的原生 MySQL 服务运行后端测试与前端构建，不使用 Docker 或服务容器。实际运行结论与链接在发生后记录，不预写通过徽章。真实 AI 调用不作为每次构建的必需步骤，另记少量真实接入结果。

## 6 需求与版本追溯

PB 编号 → 分支或任务 → 提交 → TC 执行与缺陷 → 评审版本构成追溯链。`CHANGELOG.md` 记录已交付的变化，计划内容留在待办和 Sprint 计划中。需求变更同步相关文档，实际证据链接在发生后追加。
